# عقود API والأحداث

## مصادر الحقيقة

عقد HTTP في `packages/contracts/openapi.json`، وأنواع النقل وغلاف الأحداث في `packages/contracts/src/index.ts`. التنفيذ الفعلي لكل خدمة في `src/transport/routes.ts` و `src/application`. لا يصح وصف OpenAPI بأنه إثبات تنفيذ كل شاشة؛ راجع `MIGRATION-MATRIX.md`.

البادئة العامة `/v1/{service}`؛ مثال: `/v1/crm/customers`. تستقبل الخدمة نفسها `/v1/customers` بعد إزالة اسمها في Gateway. لا تستورد خدمة controllers أو repositories لخدمة أخرى لتجاوز هذا العقد.

## الطلبات والأخطاء

- `Authorization: Bearer ...` على العمليات المحمية. claims موثقة وموقعة، وليست headers لتحديد tenant أو role يختارها العميل.
- `Idempotency-Key` للأوامر. يُولد مرة لكل نية مستخدم، ويعاد استخدامه بعد انقطاع لا يُعرف معه هل حفظ الخادم الطلب. لا يعاد استخدامه مع payload مختلف.
- أوامر تعديل السجل تستخدم النسخة المتوقعة في body وفق schema. تعارض النسخة يعيد 409 ويستلزم إعادة القراءة؛ لا يستبدل التطبيق سجلًا أحدث بصمت.
- الأخطاء على هيئة `{ "error": { "code": "VERSION_CONFLICT", "message": "Record changed", "requestId": "example" } }`. يجب أن يعالج المهايئ الحالات 401 و 403 و 404 و 409 و 503 صراحة. لا يطبع token أو بيانات الاتصال أثناء التشخيص.
- أموال الخلفية أعداد صحيحة مثل `totalMinor` و `unitPriceMinor`. واجهات البيانات القديمة تعرض قيمًا بوحدة رئيسية؛ التحويل له موضع واحد واختبار للقيم الكسرية وحدود الدقة، ولا يُستبدل الاسم وحده.
- الأوقات بصيغة ISO، وحقول التاريخ فقط منفصلة حسب schema. معرّفات الخدمات ليست افتراضًا أنها نفس IDs بذرة العرض القديمة.

عميل النقل يدعم GET وPOST وPATCH وPUT، مع تمرير رمز الدخول ومفتاح منع التكرار للأوامر. تظل مهايئات البيانات الخاصة بالواجهات وعقود كل إجراء مسؤولية منفصلة؛ وجود وسائل النقل لا يعني أن جميع الشاشات مرتبطة بالخادم.

## سياسة الإصدارات

التغييرات الإضافية المتوافقة يمكن أن تبقى في `/v1` عندما يتحملها المستهلكون الحاليون. حذف حقل، تغيير معناه أو نوعه، أو تغيير صلاحية/حالة أعمال يتطلب مراجعة توافق، وقد يحتاج `/v2` وخطة انتقال. رقم package 2.0.0 يصف الحزمة؛ لا يحول إصدار API تلقائيًا إلى v2.

التزام الإصدار يراجع: دقة OpenAPI أمام handlers، أمثلة طلب/استجابة صالحة، توافق المستهلك والمزود، واختبار نسخة سابقة من العميل. **بوابة آلية كاملة لاكتشاف جميع التغييرات الكاسرة ليست مفترضة من وجود هذا الملف**؛ تسجل نتائجها الفعلية في `VERIFICATION.md` عند إضافتها وتشغيلها.

## الأحداث والاتساق

غلاف الحدث يحمل `schemaVersion` و `id` و `source` و `tenantId` و `aggregateId` و `aggregateVersion` و `occurredAt` و `correlationId`، ويمكن إضافة `causationId`. يحتاج التغيير الكاسر إلى نوع/نسخة جديدة وخطة تعايش. تمنع قواعد المستهلك إعادة التأثير لنفس الحدث، لكن النقل قد يعيده.

يعرض العقد حالة fulfillment مستقلة حتى يصل إنشاء المشروع والفواتير. لا تعادل استجابة اعتماد العقد اكتمال جميع المستهلكين. يحتفظ النظام بأخطاء retry/dead ليتابعها المشغل. الموافقة على شروط العقد أو تسجيل الدفعة هنا سجلات نظام؛ لا تعني توقيعًا خارجيًا أو تحصيلًا مصرفيًا.
