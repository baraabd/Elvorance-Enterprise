## البنية المنفذة

Microservices في هذا التسليم هي خدمات مستقلة قابلة للبناء والنشر، وليست مجرد تقسيم ملف واجهة. توجد بوابة واحدة وسبع خدمات تملك بياناتها: الهوية، CRM، المبيعات، التنفيذ، الفوترة، التتبع، والمراسلات. لكل خدمة دور قاعدة مستقل وقراءة بيانات الآخرين عبر API أو أحداث RabbitMQ. المعاملات تكتب transactional outbox، والمستهلكون يستخدمون inbox لمنع تكرار أثر الحدث.

داخل الخدمات والواجهة فُصلت النقل والمصادقة والبيانات والنماذج والحقول والقوائم والموافقات في وحدات يعاد استخدامها. يفرض فحص الحدود منع استيراد تطبيق داخل آخر أو تجاوز ملكية الخدمة. يرفض الخادم انتحال المستأجر أو المندوب من جسم الطلب، ويتحقق من ملكية العميل الحالية، وإصدارات السجلات ومفاتيح إعادة المحاولة.

أُعيد أيضًا تنظيم منطق الاستمارة الذي يستخدمه CRM في وحدات TypeScript صارمة للأنواع والأسئلة والدليل والتحقق من التعريف والإجابات والتوصيات، مع نوع دليل مشترك في العقود بدل تعريفات متكررة. أزيل ملف declarations المتساهل الذي كان يخفي أخطاء التنفيذ؛ المدخلات التالفة والخيارات الفارغة أو غير المعتمدة تُراجع باختبارات محددة.

الأسعار والعملة والدفعات تُحسب وتُراجع على الخادم. التسعير الخاص والخصم الاستثنائي يحتاجان موافقة إدارية مرتبطة بمحتوى العرض. قبول العميل للعرض واعتماده العقد خطوتان منفصلتان؛ لا ينشأ دفع أو توقيع من زر إتمام الزيارة. أضيفت واجهات موافقة الإدارة وقرار العميل حتى لا تتوقف دورة المندوب عند إجراء لا يمكن للطرف الآخر تنفيذه.

## أدلة التحقق وحدودها

فحص شجرة المصدر المحلية قبل تثبيت التسليم نجح: `npm run verify` أنهى 211 اختبارًا (210 ناجحة واختبار PostgreSQL واحد متجاوز في التشغيل العادي)، ونجح PostgreSQL الحقيقي منفصلًا. انتهى فحص الحدود عند 22 workspace و226 ملف مصدر ضمن رسم الاستيراد دون مخالفة، والتنسيق ناجح. نجحت مسارات التصميم الـ64 وأجنحة التراجع السبعة. فحص npm لم يسجل ثغرات معروفة في هذه اللقطة؛ هذا لا يعوض مراجعة أمان التشغيل أو اختبار الاختراق.

- توجد اختبارات نطاق وHTTP وصلاحيات وتعارضات وإعادة محاولة، واختبارات DOM تتصل بمعالجات الخدمات الحقيقية. نجاحها لا يثبت قياس اللمس أو الأداء على هاتف فعلي.
- جرى اختبار PostgreSQL 16.15 فعلي مؤقت: سبع قواعد مملوكة، و42 محاولة اتصال متقاطعة مرفوضة، وسياسات RLS، وحالات التزامن والحفظ وترقيم القوائم. الاختبار العادي يتخطاه عند غياب قاعدة الاختبار؛ runner المستقل وCI ذو PostgreSQL يشغلانه فعليًا.
- جرى تسجيل دخول PKCE وتجديد وإلغاء جلسة مع Keycloak 26.8.2 حقيقي محلي عبر HTTPS. [الدليل المنقح](evidence/identity-local-verification.json) يحدد أن المتصفح الأصلي والجهاز وStaging المستضافة لم تُختبر بهذا الفحص.
- نجح [تشغيل التحقق الأصلي الأول](https://github.com/baraabd/Elvorance-Enterprise/actions/runs/44259277639) على المصدر `e5911236211daf66028b448efe009886e6f1a954`: Android lint/build و4 اختبارات instrumentation على emulator، وبناء Xcode و3 اختبارات Keychain/redirect على simulator. أُضيف اختبار تسجيل الجسر الرابع بعد ذلك؛ نتائج أحدث مصدر تُراجع في Checks داخل طلب المراجعة.
- ملفات Native verification تستخدم واجهة تحقق مخصصة بلا حسابات أو دورة مبيعات. حزمة AAB غير الموقعة وتقارير simulator الناتجة عنها أدلة على هذه الطبقة فقط؛ لا تُوزع كنسخة المندوب النهائية.
- workflow `backend-runtime.yml` يشغّل gateway والخدمات السبع وPostgreSQL وRabbitMQ عبر Compose ثم يمر من عميل تجريبي إلى عقد مستقل الاعتماد ومشروع وفاتورتين وإشعارات. بياناته مصطنعة معلنة، وهدفه محلي داخل CI، ويمنع استهداف Staging أو الإنتاج. نجاحه يُثبت من التشغيل المرتبط بـSHA في GitHub، وليس من وجود ملف الاختبار.
- `npm run test:parity` يراجع 64 مسار معاينة محفوظًا؛ هذه نتيجة عدم كسر التصميم السابق، وليست دليل نقل كل تلك المسارات إلى API. اختبارات الواجهة المباشرة منفصلة.

## النطاق الذي لا يُدّعى اكتماله

الموقع أمامي ومشروط بالموافقة؛ لا يوجد تتبع خلفي دائم. الإشعارات داخل التطبيق؛ لم تُركب خدمة تسجيل أجهزة FCM/APNs. قراءة الفواتير والمدفوعات لا تعني تحصيلًا عبر مزود دفع. خطة الزيارات قائمة مرتبة محفوظة، ولا تدعي تحسين المسار أو الملاحة.

المستودع يحتفظ بالمعاينة القديمة وأدوات لها `@ts-nocheck`: أحصى التدقيق 95 ملفًا من أصل 335 ملف مصدر في نطاقه. تقرير `audit:migration` يستمر في إعلان `acceptanceComplete: false` ما دام ذلك قائمًا. مدخل إصدار المندوب يستبعد runtime المعاينة وبياناتها، لكن هذا لا يثبت أن المستودع كله خالٍ من كل دين تقني أو خطأ محتمل. لا توجد شهادة «نظيف 100%» أو ضمان صفري للأخطاء.

المعاملات الحالية تستخدم أقفالًا حسب الخدمة والمستأجر لحماية قواعد العمل؛ توجد حدود للاستعلامات الداخلية، وتجمع واجهة القوائم الصفحات عند العرض. لذلك يلزم قياس الحمل بحجم بيانات وأجهزة واقعي، واختبار إعادة معالجة الأحداث والتعافي واستعادة النسخة الاحتياطية قبل اعتماد التوسع الإنتاجي.

## العوائق الخارجية والخطوة التنفيذية التالية

تطبيق حزمة Railway أعاد حرفيًا: `Cancelled — the user did not approve this action. No changes were made.` ظلت خدمتا الهوية وقاعدتها `staged-create`، ولم يُنشأ Deployment. لم تُستخدم وسيلة أخرى لتجاوز هذا الرفض. بعد السماح بتطبيق الحزمة، تُستكمل الخدمات والعناوين وفق [دليل Staging](REP-STAGING-OPERATIONS.md)، ثم تُبنى النسخ الموقعة من العناوين الحقيقية.

توضع أسرار التوقيع في GitHub Environments أو مدير أسرار معتمد؛ لا تُرسل مفاتيح خاصة في محادثة ولا تدخل المستودع. تُختبر النسختان على الأجهزة الفعلية، وتُجمع أدلة قبول المصدر والصور والنسخ المختبرة. مولّد الإنتاج وworkflow الإصدار يرفضان النقل قبل التقرير المُراجع. راجع [دليل الهاتف](rep-native-release.md) و[عقود API](REP-BACKEND-API.md) للأوامر والحقول المطلوبة.
