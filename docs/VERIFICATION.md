# التحقق وحدود الأدلة — Enterprise 2.0

**تصحيح 2.0.1:** النتائج التاريخية أدناه تخص إصدار 2.0.0. راجع [نتائج التصحيح](RELEASE-2.0.1.md) و[تشخيص Windows وأوامر الحل](WINDOWS-TROUBLESHOOTING-2.0.1.md) للأعطال المكتشفة لاحقًا ونتائج الاختبارات الجديدة. نجاح 2.0.0 على Linux لم يثبت عمل أدواته على Windows.

## إعادة فحوص البنية

```bash
node --test tests/architecture/boundaries.test.mts tests/architecture/infra-helpers.test.mts
node tooling/scripts/check-boundaries.mts
npm run test:parity
npm run test:regression
```

اختبار smoke داخل المجموعة يستعمل fetch stub. تشغيل `node infra/compose/smoke.mts` ضد Gateway حقيقي بوابة مستقلة من 9 قراءات؛ لا يُحتسب اختبار stub دليل HTTP شبكي. تحليل Compose وسلامة Shell يثبتان صحة النص المفحوص، ولا يحلان محل `docker compose config` وبدء الحاويات.

## معنى نتيجة PostgreSQL

يختبر `tests/backend/postgres.test.ts` قواعد حقيقية مؤقتة، ومعاملات rollback، و FORCE RLS حتى على دور المالك، و outbox/inbox، ومنع إنشاء عقدين أو مشروعين أو فواتير مكررة، وتعارض دفعات متزامنة. يستعمل Fastify inject ومعالجة المستهلك داخل العملية؛ قاعدة البيانات حقيقية، لكن RabbitMQ والنقل بين العمليات ليسا جزءًا من هذا الإثبات.

يقبل الفحص `ELVORANCE_TEST_POSTGRES_URL` لقاعدة اختبار إدارية مؤقتة؛ **لا تستخدم عنوان قاعدة تشغيل أو إنتاج**. عند غياب المتغير يُسجل الفحص متخطى في التشغيل العام؛ لا يتحول ذلك إلى نجاح قاعدة بيانات. يقدم `tests/backend/run-postgres.mts` مسارًا اختياريًا عبر embedded-postgres مثبت خارج الاعتماديات المعتادة، أو من خلال `ELVORANCE_EMBEDDED_POSTGRES_MODULE`. سجل تشغيله يميز هذه النتيجة من تشغيل Compose. النتيجة المثبتة في `tests/backend/verification.json`، وعقد HTTP في `packages/contracts/openapi.json` مع حصر العمليات في `route-inventory.json`.

## بوابات تحتاج Docker وبيئة تشغيل فعلية

1. نسخة نظيفة: `npm ci` ثم `npm run verify` ثم `docker compose … config --quiet` و `up --build`.
2. خروج كل مهاجر بالرمز 0 وجاهزية الخدمات السبع، ثم smoke الحقيقي. جاهزية Gateway وحدها لا تثبت جاهزية upstreams.
3. تنفيذ `infra/compose/postgres/check-isolation.sh` داخل حاوية PostgreSQL للتأكد من أن إعداد Compose نفسه يسمح بسبعة اتصالات ويمنع 42 اتصالًا. نجاح اختبار PostgreSQL المستقل لا يشغل هذا script تلقائيًا.
4. رحلة العرض والعقد والمشروع والفواتير عبر HTTP و RabbitMQ، مع انتظار fulfillment بدل افتراض اكتمال جميع الخدمات فورًا.
5. إعادة الطلب وتسليم الحدث، وتعطل الوسيط وإعادة تشغيل الخدمات، وعدم إنشاء مشروع أو فاتورة أو دفعة مكررة.
6. ترحيل قاعدة تحتوي بيانات، واستعادة نسخة احتياطية، وتدوير الأسرار، وفحص صلاحيات مستأجر آخر.

الأوامر العملية موجودة في دليلي Windows و Linux. يظل كل بند غير منفذ موصوفًا بذلك؛ مرور اختبارات الذاكرة أو AST لا يغير حالته.

## حفظ التصميم والأجهزة الأصلية

خط أساس v1.1 السابق كان 159 حالة، منها 22 للخادم القديم، إضافة إلى 64 مسارًا. حصر الإجراءات 122؛ مجموعة workflow وحدها نفذت 38 معالجًا مختلفًا. هذه أرقام نطاق، وليست إثبات فحص كل احتمال. تختبر مجموعة regression الحالية 137 حالة من الوحدات المستخرجة؛ الخلفية الجديدة لها مجموعاتها المستقلة.

مرجع parity الحالي يحفظ DOM والأصول تحت fixtures ووقت ثابتين. يحتاج الادعاء بمطابقة بصرية لكل شاشة إلى لقطات قبل/بعد في المحرك والأبعاد نفسها، وانتظار الخطوط، وفحص الأزرار والحقول والمربعات وحالات الخطأ. تراجع الفروق قبل تغيير baseline. تبقى تجربة WebView ولوحة المفاتيح و safe areas وأذونات الموقع و iOS اختبارات أصلية منفصلة.

## حدود فحص الاعتماديات

يقرأ المدقق manifests و JS/TS، ويحل tsconfig paths و package imports والمسارات النسبية، ويمنع الاعتماديات غير المعلنة والحزم غير المصنفة والدورات. لا يوجد استثناء شامل للخدمات أو اختباراتها. لا يفحص SQL وقت التشغيل أو سياسة الشبكة أو كل وسيلة تنفيذ شفرة اعتباطية؛ لهذه الحدود بوابات منفصلة.

راجِع `MIGRATION-MATRIX.md` قبل وصف التطبيق بأنه مرتبط بالخادم بالكامل. الواجهات الحالية demo adapter، والخدمات تنفذ رحلة مرجعية مستقلة؛ الفصل البنيوي لا يخفي بقية أعمال التكامل.
