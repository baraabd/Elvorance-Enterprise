# مصفوفة الانتقال — ما بقي محليًا وما أصبح خدمة

هذه مصفوفة قبول للبنية 2.0. المقصود بـ«منفذ في الخلفية» وجود handler وقاعدة أعمال في الخدمة المالكة؛ لا يعني أن الشاشة الحالية تستخدمه. تطبيقات العرض تضبط `dataMode: "demo"` و `siteTracking: false` في `config.example.ts`، ولا يصنع تغيير قيمة الإعداد مهايئًا مكتملًا تلقائيًا.

## حدود يجب أن تبقى ظاهرة

1. واجهات 1.1 كانت تشارك `localStorage` على الأصل نفسه. تطبيقان داخل حاويتين native منفصلتين لا يتشاركان ذلك المخزن؛ توحيد البيانات بينهما يتطلب الخلفية ومهايئاتها.
2. `/api/tracking/*` في النسخة المستضافة السابقة ليس alias تلقائيًا لـ `/v1/tracking/*`. لا يُخلطان في دليل التشغيل أو تقارير النجاح.
3. `packages/api-client` طبقة نقل جاهزة للاستعمال، وليست مهايئًا سحريًا لجميع 122 معالجًا قديمًا.
4. مجموعات الاختبار القديمة 159 حالة و 64 مسارًا هي خط أساس النسخة السابقة، ولا تستبدل اختبارات الخادم/الهوية/التزامن أو الأدلة الجديدة للتطبيق المحمول.
5. الفصل إلى workspaces والخدمات لا يثبت صلاحية التشغيل الإنتاجي وحده. تبقى بوابات Docker و RabbitMQ الحي و native و visual QA موثقة حسب ما نفذ فعلًا.

## قالب قبول لكل feature تنتقل إلى API

يسجل صاحب feature: المسارات والمعالجات المتأثرة، الخدمة المالكة، request/response schema، صلاحيات الدور وملكية السجل، مفتاح التكرار والنسخة، حالات التحميل والفشل، سياسة cache/offline، واختبارًا بين جلسات مستقلة. يكتمل الربط عندما تُقرأ نتيجة الحفظ من تطبيق آخر عبر الخادم، وتظل النتيجة صحيحة بعد إعادة التشغيل وإعادة الطلب والتعارض، مع حفظ التصميم المرجعي.
