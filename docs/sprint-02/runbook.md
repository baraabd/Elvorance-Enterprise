## Backup limitations and operator decisions

The new retention mode is invoked by acceptance/recovery, not a separately deployed recurring backup service. A dedicated daily backup job and provider retention lifecycle are still to be provisioned after approval. Proposed operating targets for approval: daily backups, 14-day retention, RPO no more than 24 hours, RTO no more than 60 minutes; none is an achieved or measured SLO. Current logical dumps are per-database snapshots, not a cross-service atomic transaction or PostgreSQL PITR. No Keycloak full database restore, broker volume restore, off-region copy, key-loss recovery or immutable bucket retention is claimed. Dumps above 32 MiB fail deliberately rather than exhausting the small staging worker; production-size streaming/multipart backup is separate work.

Objects are encrypted before upload and authenticated on download. Each object is bound to its source/run/service context. PUT uses a no-overwrite precondition; no automatic object deletion or bucket credential reset is performed. Store encryption key recovery material outside the bucket and restrict job credentials. Never replace or erase a live database to test restore.

## Rollback

Stop the rollout, leave failed readiness truthful and preserve evidence. Revert application image/revision per service to the captured pre-change source; preserve database volumes, queues, bucket objects and additive ledger columns. Do not run down-migrations or remove checksums. A release with an unknown applied migration must fail its migration check rather than silently downgrade. If a data recovery is required, restore to new databases, validate ownership/RLS and row digests, then seek separate approval for an application connection switch.

The recorded pre-change gateway state was already **503**. Returning to it restores the previous revision, not guaranteed service health. Prefer a reviewed forward fix if rollback reproduces the known unbound-event problem. The additive audit queue can safely remain during application rollback; do not purge its data. Vercel previews can be withdrawn or rolled back only within the new staging projects; keep existing Railway web URLs as fallback. Do not move production aliases. Cleanup deletes only the new, run-scoped rehearsal databases tracked by the operation; failed cleanup is a blocker and must be reported.
