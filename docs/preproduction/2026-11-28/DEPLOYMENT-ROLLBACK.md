# Staging rollout and rollback runbook

## Fixed boundary

Repository: `baraabd/Elvorance-Enterprise`.
Railway project: `075e27d5-8edc-4ddd-8f27-a5eea3ef5d5a` (`elvorance-staging`).
Environment: `49c49479-0810-491c-99cb-fc52ca547c04` (`staging`).
No command in this procedure authorizes a Production environment, store upload, database overwrite or destructive replay.

## Preconditions

Record the exact candidate SHA/tree, complete CI decision and all current service deployment IDs, image/source identities, applied migration versions and public hostnames. Verify the environment has no unrelated pending changes. Keep an authorized operator and incident owner available. Do not copy secret values into the manifest.

Deploy only the operations service first, pinned to the tested candidate, with `STAGING_OPERATION=backup-restore`. Reuse existing private database and protected backup credentials; never generate a replacement encryption key to make an old archive readable. Require eight database receipts, exact row/RLS matches, retained manifest retrieval and successful scratch cleanup. Preserve the encrypted object keys/digests and the encryption-key custody reference separately. A failed or partial run blocks schema rollout.

## Service rollout

1. Review additive migrations from the current deployed source to the candidate. Existing applied SQL must remain unchanged. Back up before any new migration.
2. Pin upgraded consumers first: Communications must understand the newly bound events; Billing must understand the additive subtotal/discount contract. Run each owning service's normal migration pre-deploy and verify its readiness/logs before proceeding.
3. Upgrade remaining domain services, then Gateway, then the three explicitly server-only web builds. Do not use the ordinary demo build as the hosted product. Do not change database ownership or share credentials across services.
4. Observe CRM pending outbox publication and convergence without rewriting historical events. Investigate dead letters individually; no arbitrary bulk replay.
5. Match every deployed source to the same candidate and verify public health/readiness, real OIDC, allowed/denied tenant/owner journeys and all three web roles.
6. Run bounded hosted acceptance, realistic approved performance tests, recovery and signed device acceptance. A successful deployment status or a liveness HTTP 200 is not business acceptance.

Every source/configuration change is scoped to the exact staging environment, staged before applying, and reviewed as a complete diff. Do not apply a patch containing unrelated changes.

## Stop conditions

Stop on failed migration/checksum, lost backup integrity, readiness failure, authorization/tenant leakage, duplicate commercial side effects, non-converging outbox, unexpected dead-letter growth, or data invariants breaking. Keep the failing deployment and its sanitized logs as evidence. Do not repeatedly rerun writes with new idempotency keys.

## Application rollback

Use the recorded previous immutable deployment only after checking it supports the additive schema and event contracts now present. New consumers may need to stay active when an old producer is rolled back. Do not automatically run old migrations against a newer schema. Roll back the affected application tier only; preserve database volumes and broker queues. Re-run read-only readiness and the designated smoke journey. An untested rollback is a plan, not completed recovery evidence.

## Data recovery

Do not restore over a live database merely because an application rollback failed. Declare a maintenance boundary, preserve the current database/queue evidence, and obtain explicit destructive-recovery approval. First retrieve the retained encrypted archive, verify object digest and exact manifest context, authenticate/decrypt, and restore into a NEW isolated database. Validate rows, ownership, RLS, idempotency, inbox/outbox, and financial balances. Reconcile cross-service events before any cutover. The automated drill only creates `elvorance_restore_<12-hex>_<domain>` databases and deletes its own scratch copies; it cannot switch live service URLs.

## Release record

Keep source SHA/tree, CI run/attempt/artifact digests, service deployment IDs, migration versions, backup receipts, hosted test results, device model/OS/signed binary hashes, independent reviewer and owner decision. Set Production GO only when every mandatory gate is backed by that candidate's evidence. Missing external approvals are not generated by code.
