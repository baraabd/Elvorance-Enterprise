## Delivered changes

### Identity and storage

- Preserve `oauth4webapi` Authorization Code + S256, state/nonce, authorization-response issuer checks, JWKS signature verification, strict discovery origins, refresh rotation, subject binding and cancellation/logout race protection.
- Add `elvorance-client-staging` / `elvorance-client-production` public native clients. They receive **only client roles**, distinct from representative and administrative clients; disable implicit/password/device/CIBA/token-exchange/service-account grants as already done for the representative. New native callbacks are `com.elvorance.client.staging:/oauth2redirect` and `com.elvorance.client:/oauth2redirect`.
- Port the existing representative native bridge into the client hosts by application-identity substitutions, without changing the proven cryptographic implementation. Android: Custom Tabs, Android Keystore AES-GCM, record-specific AAD, atomic no-backup ciphertext files, no cleartext fallback. iOS: ASWebAuthenticationSession, bundle-scoped non-synchronizing Keychain with `WhenUnlockedThisDeviceOnly`. Native code pins callback identity to the installed app; shared TypeScript accepts only the two registered native-app shapes for the selected environment.
- Source parity tests prevent the two native cryptographic implementations silently diverging. This is intentionally a checked port, not an untested cryptographic rewrite; a future shared native module is preferable to permanent duplicated maintenance.
- Web session/refresh records remain memory-only. Only an environment/client-scoped PKCE transaction uses sessionStorage; the existing vault enforces its five-minute age and one-time consumption. New tests prove no authentication access to localStorage, no session credential persistence, isolation of transaction keys and callback URL cleanup. A full page reload requires authentication again; this is not persistent web SSO.
- Extend the real loopback Keycloak suite to **rep-native, client-native, admin-web and client-web**. Each exercises code+PKCE, verified claims, role-scope restriction, refresh rotation/reuse rejection, local logout, and rejection of a freshly revoked refresh token. This provider suite is scheduled in FULL-CI; local unit tests are not substituted for it.

### Backend authorization and isolation

- The existing 84-operation `packages/contracts/route-inventory.json` is now an executable deny-by-default role policy. Every protected domain route must have a declared policy at registration; onRequest authenticates and checks it **before** the handler. HEAD inherits GET policy. Unknown registered policies fail startup. Empty role sets cannot reach business handlers even when ownership IDs remain present.
- Existing per-resource ownership, assignment rechecks, commercial-state constraints, tenant transactions and cached-idempotency authorization remain in place. Role-matrix tests are 588 coarse policy decisions (84 × six real roles plus no-role); they are **not 588 end-to-end business/IDOR journeys**.
- Reject future-issued access JWTs beyond the existing five-second clock tolerance; bound subject length. Continue to require verified issuer, audience, signature, expiration, issuance, tenant and recognized role claims. Neither spoofed tenant/role headers nor cookies establish an API identity.
- Append new migrations, without modifying prior migration SQL, adding ENABLE/FORCE RLS and USING/WITH CHECK policies to `inbox` and `idempotency_keys` in all seven owned databases. Versions: identity 3, CRM 4, sales 3, delivery 2, billing 2, tracking 2, communications 3.
- Request transactions reject PostgreSQL SUPERUSER/BYPASSRLS roles before processing tenant data. Extend the existing real PostgreSQL suite: metadata-table policy flags in every database, raw-owner no-context/cross-tenant reads and modifications, foreign-tenant INSERT rejection, transaction context reset, own-tenant cached results and unsafe privileged runtime-role rejection. Existing 42 denied cross-service connections and domain IDOR/assignment tests remain mandatory.
- **Outbox is intentionally not tenant-RLS-protected**: the current service-owned publisher leases work across tenants. It remains a trusted worker surface, not an isolation claim against a compromised worker.

### API boundary and audit

- Reject an explicit non-allowlisted Origin before forwarding a mutation; continue exact-origin CORS without credentials. Native origins `capacitor://localhost` and `https://localhost` must remain explicitly configured. No-Origin native/server callers still require verified bearer authentication. CORS is not authentication.
- The current API uses bearer headers, not automatically sent session cookies. Cookie-only tests fail 401. The relevant login CSRF controls remain OIDC state, nonce, PKCE and pinned callbacks. Cookie/BFF introduction requires a fresh CSRF/SameSite review rather than assuming this design remains adequate.
- Add bounded per-process fixed-window budgets: 600 requests/socket-IP/minute, 300 requests/verified (tenant, subject)/minute, at most 10,000 active keys. Return 429 and Retry-After. Never derive identity from caller X-Forwarded-For/tenant headers; never evict live counters to accommodate a new key. This is not a distributed rate-limiting service.
- Add allowlisted JSON `security.audit` events for protected API attempts: server request ID, service, route **template**, method, status/outcome and verified actor/tenant. Exclude raw URLs, queries, payloads, credentials, cookies and authorization headers. Disable automatic raw request logs and sanitize error logging. Preserve Keycloak events/admin-events without detailed administrative payloads.
- Audit is operational structured logging, **not** an immutable, acknowledged, transactionally atomic audit ledger. No persistence/retention guarantee is claimed.

No suppression/coverage baseline was relaxed; new code uses no new type suppressions, explicit any or non-null assertions. Native bridge source tests are not emulator/device execution. Client reports are uploaded separately from the existing representative evidence totals. A passing aggregate requires these new steps to succeed, but native signed physical-device acceptance remains outside this evidence.

1. Review this PR and exact source SHA independently. Require the full existing CI gate plus new client native/provider/metadata checks; inspect failures and skips, not only a green badge.
2. In an approved isolated staging environment, back up each owned database, record migration checksums, apply the additive versions above with the migration job, and verify both request-role safety and metadata RLS using non-privileged accounts. Do not rewrite existing applied migrations.
3. Review the new native-client realm definition, callbacks, scopes and administrator-only claim mappings. Existing provisioning remains fail-closed on drift; it must not be run expecting automatic mutation of an already managed realm. Prepare an explicitly approved additive provider change, or bootstrap a new isolated realm, then run the hosted acceptance flow.
4. Configure exact web and native CORS origins, HTTPS gateway/issuer, the app's matching environment/client/callback and the native plugin authorization endpoint. The generic app build still copies demo/example settings: do not publish it as a configured production app. No client release/signing pipeline is asserted here.
5. Test tenant A/B and same-tenant different owners on actual apps; refresh after network loss, app restart, logout during rotation, locked device, reinstall/backup behavior, and consent/authorization changes. Record signing identity, app source hash and provider configuration without tokens.
6. Observe audit delivery, retention/access restrictions and limits behind the actual reverse proxy. Confirm no staging endpoint reaches production resources. Any deployment remains a separate approved operation.
