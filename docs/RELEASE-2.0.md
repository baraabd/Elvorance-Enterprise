# تسليم Elvorance Enterprise 2.0

## ما تحتويه الحزمة

المصدر قابل للتثبيت مستقلًا من مجلد `Elvorance-Enterprise`. يضم 20 workspace: ثلاثة تطبيقات، وتسع حزم مشتركة، وثماني عمليات خلفية مستقلة تشمل Gateway. تضمن الحزمة Android وiOS لتطبيق المندوب وتطبيق العميل، وإعدادات التشغيل وقاعدة التصميم والعقود والاختبارات والوثائق. لا تحتوي على `node_modules` أو كلمات مرور تشغيل أو مفاتيح توقيع تطبيقات.

التصميم الحالي حُفظ عبر استخراج 32 وحدة وظائف، و64 مسارًا، و122 معالج إجراء. تعمل الواجهات بـ HTML/CSS وJavaScript ES Modules، وتعمل الخدمات والعقود وعميل API بـ TypeScript. مجلد `preview` يحتوي نسخ HTML للمراجعة؛ للتطوير استخدم `npm ci` ثم `npm run dev`.

## الحالة التشغيلية الدقيقة

الواجهات المحفوظة تستخدم مهايئ التجربة المحلية، مع بيانات وهمية جاهزة. الخلفية تنفذ رحلة مستقلة مختبرة من العميل والزيارة إلى عرض السعر وقبول العميل واعتماد العقد ثم المشروع والفواتير والأقساط والتسليمات. الربط الكامل لكل شاشة وأمر بالهوية وواجهات الخدمات محدد في `MIGRATION-MATRIX.md`، ولا يُعلن وضع `server` للواجهة قبل اكتمال ذلك الربط.

المعاينة المنشورة تُشغّل الواجهات الجديدة، وتحافظ على خدمة الموقع الخاصة بالمعاينة. خدمات PostgreSQL/RabbitMQ تُشغّل بصورة مستقلة من `infra/compose`؛ لا تحول المعاينة مستضيف الويب الواحد إلى ثماني خدمات منفصلة.

لم تتوفر Docker أو بيئة Android Studio/Xcode في جلسة الإعداد. لذلك لا تُنسب لهذه الجولة تجربة RabbitMQ حي أو بناء APK/IPA أو اختبار جهاز فعلي. اختبار PostgreSQL استُخدم فيه خادم حقيقي محلي، واختبارات النقل شملت محاكاة AMQP؛ التفاصيل محفوظة منفصلة. يتطلب التشغيل الإنتاجي مزود هوية OIDC وإعداد البيئة وربط المميزات المبينة في مصفوفة الانتقال.

## من أين تبدأ

1. شغّل التطبيقات عبر README ودليل نظام التشغيل.
2. اقرأ `ARCHITECTURE.md` وحدود ملكية البيانات وADRs قبل تغيير خدمة.
3. استورد `packages/contracts/openapi.json`؛ يحتوي 56 عملية موزعة على 46 مسارًا.
4. طوّر feature واحدة بواجهات `packages/api-client` وعقود الخدمة المالكة، وأبقِ مكونات العرض مشتركة.
5. شغّل `npm run verify` و`npm run check:format` قبل اعتماد التغيير؛ workflow المرفق يهيئ PostgreSQL مؤقتًا في CI أيضًا.
